The simobserve task (simulation Phase 5c, #841): CASA 6.7.6’s task_simobserve.py, ported as its specification (ADR-0018) onto the simulator session (Simulator) and the simutil helpers (crate::simutil).

simobserve runs the task’s stages in CASA’s order, each in its own module:

  • the run itself: the mode, the project directory and the files’ stem <project>.<configuration> (Run);
  • the sky model: modifymodel and flatimage of skymodel, or the component-only .compskymodel (sky);
  • the antenna list: ALMA resolution strings, the search through the project directory, the path given and CASA’s alma/simmos, the primary beam and the resolution (antennas);
  • the pointings: laid out or read, written to <stem>.ptg.txt, and checked against the model (pointings);
  • the calibrator and the observing schedule (schedule);
  • the observation: the session’s setters, observe, predict and the rest frequencies (observe);
  • leakage and thermal noise on copies of the MeasurementSet (noise).

The files are CASA’s: <stem>.skymodel and .skymodel.flat (or .compskymodel and .compskymodel.flat), .ptg.txt, .cal.cclist, .ms (or .sd.ms), .fullpol.ms and .fullpol.cal, and .noisy.ms, .noisier.ms or .noisy.sd.ms. Graphics (.skymodel.png, .observe.png, .quick.psf) come in Phase 5e; until then graphics writes none and says so.

Where CASA raises, the task returns SimobserveError with CASA’s message. Where CASA’s task does something physically wrong, casa-rs departs from it, each departure recorded in docs/CASA (C++) bugs.md:

  • A calibrator’s last pass. With a calibrator, CASA observes each pass over the map only when it completes, so a totaltime that ends inside a pass drops that pass, and one shorter than a pass observes the calibrator alone. casa-rs observes the pointings the time allows.
  • The calibrator’s scans. CASA selects the map’s fields before predicting (setdata(fieldid=range(nfld))), which leaves the calibrator’s scans unpredicted. casa-rs predicts every scan.
  • Two component lists. With a calibrator and a complist, CASA predicts from the two lists’ names joined by a comma, which is not a table, so its predict fails and the MeasurementSet is left unpredicted. casa-rs predicts both lists.
  • <stem>.noisier.T.cal. CASA deletes the Tsys table tsys-atm writes beside .noisy.ms and .noisy.sd.ms but leaves the one beside .noisier.ms; casa-rs writes none.
  • Pointings of no length. Pointing times summing to zero (an integration of 0s) make CASA’s observing loop run forever; casa-rs refuses them.
  • A total-power MeasurementSet. Corrupting an existing MeasurementSet, CASA takes it for total power when any UVW value is zero (uvw.all() == 0); casa-rs when every one is, as was meant.
  • A sky model the task writes. A skymodel that is the <stem>.skymodel the task writes is deleted by CASA before it is read; casa-rs refuses it.
  • A project path. CASA names the files <project>.<cfg> inside the directory <project>, which nests a path inside itself; casa-rs names them by the directory’s last component.
  • A link in the project. CASA writes the pointing file through a symbolic link in the project directory, replacing or creating the file outside the project that it names, and fails on a link to a table it replaces (shutil.rmtree refuses links). casa-rs replaces the link itself (make_way) and counts a dangling link as an existing file.

A predicted model under the primary beam holds one grid per field (the session’s Simulator::predict), so a mosaic of many pointings over a large model can need more memory than the session’s budget, which refuses it before it starts.

CASA’s MeasurementSet time selection: the timerange expressions of casacore’s MSSelection, ported from MSTimeGram.ll, MSTimeGram.yy and MSTimeParse.cc at casacore aaf72eb7, the commit CASA 6.7.6.14 builds.

resolve_time_selector turns an expression into a TimeSelection: the conditions on the MAIN TIME column that MSTimeParse builds as TaQL, with the same double-precision constants. TimeSelection::holds then tests a row’s TIME exactly as CASA’s TaQL does. MSSelection ANDs the time conditions with the conjunction of its other expressions, which is the caller’s part.

§Forms

A timerange is one or more comma-separated terms; a row is selected when any term holds (MSTimeParse::addCondition, MSTimeParse.cc:188-196). With t, t0, t1 the term’s times in seconds and e the default row’s EXPOSURE (see Defaults):

The edge width w is a C Float (MSTimeEdgeBuffer, edgeWidth_l), so it is rounded to single precision; N must be written with a point (3.0[ or 3.[), since the grammar takes only an FNUMBER there and 3[ is a parse error. 0.0[T0~T1] is the open interval. A range whose lower bound exceeds its upper bound is refused (MSTimeParse.cc:256-258).

Seconds keep whole milliseconds, truncated (splitSec, MSTimeGram.yy:97-104): 1.001 is the double 1.000999... and keeps 0 ms, and 2.501 keeps 500. Only the year, month (1 to 12) and day (1 to 31) are checked, with years before 1858 refused (MSTimeParse::validate, MSTimeParse.cc:388-411); other values roll over arithmetically, so 2017/02/29 is March 1 and 08:59:60.5 is 09:00:00.5.

In T0~T1, every field missing from T1 is copied from T0 once T0 has its defaults (copyDefaults), so 09:00:00~10:00:00 is on one day and 23:00:00~01:00:00 is refused. In T0+dT, dT is read as a time with the MJD epoch’s defaults (1858/11/17, zero time of day) and its MJD is added to T0’s in MVEpoch day arithmetic, so +10 is 10 s, +1:00 is one minute and +48:00:00 two days. There are no numeric MJD forms, units or signs: 57813.375, 10s, - and 2017-03-01 are parse errors. Spaces, tabs and newlines between tokens are ignored, but only the empty string selects everything; a blank expression is a parse error, as in CASA.

§Defaults

Each term reads its defaults from one MAIN row (MSTimeParse::getDefaults, MSTimeParse.cc:114-184): the row’s TIME, split into year, month and day by MVTime and into hour, minute and second by casacore’s Time, with the milliseconds (Int)((t0 - t1) * 1E3) truncated, and the row’s EXPOSURE (e). On MSSelection’s path the first term reads the first logical row (msselection_first_logical_row) and every later term reads row 0: getDefaults searches only on its first call and otherwise keeps firstLogicalRow = 0 (MSTimeParse.cc:116-120). TimeSelectorDefaults carries both rows.

§Time scale

The expression’s times are compared with TIME in whatever scale TIME holds. MSTimeParse::toTAIInSec (MSTimeParse.cc:339-344) despite its name converts nothing (its MEpoch::Convert to TAI is commented out), so a UTC TIME column is selected by UTC times, with no leap-second offset.

§Not ported

The grammar keeps the bracket state in process globals that a failed parse inside brackets leaves set, so CASA’s next unbracketed range in the same process is edge-inclusive; each parse here starts afresh. A seconds value or a year beyond C Int arithmetic, and a default row whose TIME is not a finite day number, are undefined behaviour in the C++ and are refused.

§Evidence

resources/casa-compat/evidence/msselection-time-casa-20261102.json holds the rows CASA 6.7.6.14’s ms.msselect keeps for 1528 expressions (curated forms, seeded random ones, first-logical-row and later-term defaults, and defaults rebuilt from assorted sub-second row times), written by tools/casa-compat/time_selection_oracle.py; the tests replay every one.

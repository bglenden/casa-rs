    AW-projection pairs the partner hand's visibility with the conjugate-baseline cell¶

    • Date noted: 2026-10-09
    • Status: likely CASA bug; casa-rs follows it for parity (#667, PR #668)
    • Affected code:
    • casatools/src/code/synthesis/TransformMachines2/AWVisResampler.cc (getConvFunc_p, DataToGridImpl_p, GridToData)

    Summary¶

    For a row with w ≤ 0, getConvFunc_p selects the conjugate-baseline cell of the outer correlation's Mueller element (conjMNdx, the partner hand: RR ↔ LL, RL ↔ LR), and DataToGridImpl_p then grids the visibility of the selected cell's hand (visVecElement = muellerElement % nDataPol), not the outer correlation's. The RR grid receives RR × conj(CF_RR) for w > 0 and LL × CF_LL for w ≤ 0; GridToData likewise reads the partner's model grid into the outer visibility. Stokes I of an unpolarized source is unaffected (the two hands are equal); per-hand grids of data whose hands differ, such as a circularly polarized source, mix the hands on the w ≤ 0 rows.

    Why this looks like a bug¶

    The Mueller element of a real power pattern has a Hermitian transform, so the RR kernel at −|w| is the conjugate of the kernel of the mirrored RR beam at +|w|; for the EVLA squint (R and L beams offset in opposite directions) the mirrored RR beam is the LL beam, which is why the partner cell stands in for the conjugate. The visibility being convolved is still the outer hand's. The index muellerElement % nDataPol returns the column of the selected cell's own element instead of the column of its position in the conjugate Mueller matrix.

    Effect¶

    On refim_mawproject (CASA 6.7.6.14, Stokes I, wbawp=True, conjbeams=True) the two pairings differ by 3.06e-3 normalised RMS in the dirty image. casa-rs compiles CASA's pairing (casa-imaging-operator, aw::routing into MuellerRouting) and agrees with CASA to 2e-7.

    AW-projection predicts with the unrotated w¶

    • Date noted: 2026-10-09
    • Status: CASA inconsistency between gridding and prediction; casa-rs follows it for parity (#667, PR #668)
    • Affected code: AWVisResampler.cc (GridToData reads vbs.vb_p->uvw()(2, irow); DataToGridImpl_p reads the rotated vbs.uvw_p)

    Summary¶

    AWProjectFT hands the resampler the uvw rotated to the image phase centre and the phase shift (vbs.uvw_p, dphase_p) together with the VisBuffer (vbs.vb_p). GridToData selects its w-plane and tap conjugation from the VisBuffer's unrotated w while placing the sample at the rotated u, v with the rotated phasor; DataToGridImpl_p uses the rotated w for both. The two differ only where the rotation moves a w across a plane boundary or through zero. casa-rs carries the unrotated w per row (RowContext::original_w_m, ConvolutionFunctionSet::prediction_w) and keys the AW prediction on it.

    importvla stale VLACDA cache crash on old VLA export data¶

    • Date noted: 2026-04-15
    • Status: likely CASA importvla bug
    • Affected code:
    • casatools/src/code/nrao/VLA/VLACDA.cc
    • casatools/src/code/nrao/VLA/VLABaselineRecord.cc
    • NRAO Archive file: AG189_1_46325.23029_46325.80807.exp
    • Standalone note: casa-importvla-vlacda-offset-zero.md

    Summary¶

    importvla can abort on old VLA export data when a CDA is valid in one logical record and absent in the next. The immediate failure is the offset != 0 assertion in VLABaselineRecord::attach().

    Likely mechanism¶

    VLALogicalRecord::read() reattaches all four CDAs on every logical record. VLACDA caches baseline-record objects, so if a CDA was populated on one record and then becomes absent on the next, VLACDA::attach() can try to reattach cached baseline objects using offset 0, which triggers the assertion in VLABaselineRecord.

    Proposed fix¶

    In VLACDA::attach(), if the new CDA is invalid (itsOffset == 0, or equivalently no baseline data are present), clear the cached baseline objects and return before any reattach path runs.

    mstransform channel-mode transformed-grid inconsistency¶

    • Date noted: 2026-04-10
    • Status: likely CASA mstransform bug or long-standing implementation quirk
    • Affected code: casatools/src/code/mstransform/MSTransform/MSTransformRegridder.cc

    Summary¶

    In the transformed mode="channel" / regridQuant == "freq" path, CASA appears to anchor the output-grid start edge using transCHAN_WIDTH[firstChan], while it spaces the uniform output grid using transCHAN_WIDTH[0].

    That is inconsistent once the frame transformation causes per-channel widths to vary slightly across the SPW. In the EVLA refim_Cband.G37line.ms repro case used during parity work, this produced an output-axis offset of about 0.046 Hz.

    Why this looks like a CASA bug, not a casacore bug¶

    Direct Rust-vs-casacore measures conversion for the relevant TOPO -> LSRK path matched to about 0.0015 Hz, so the underlying frame conversion itself does not appear to be the source of the discrepancy. The remaining offset is introduced later by CASA's transformed-grid construction policy in mstransform.

    Notes¶

    • This is scientifically tiny in the observed repro, but it is semantically inconsistent.
    • The effect shows up in transformed channel-mode cubes where the transformed widths differ slightly across the SPW.

    Related references¶

    • casacore PR #1464: Fix missing frame bias in IAU2000 JNAT<->APP conversions
    • casacore issue #1465: Unit mismatch in setMaximumCacheSize: bytes passed where MiB expected

    Those casacore links are not the same bug, but they came out of the same cross-checking and parity work that surfaced this CASA-side issue.

    CASA Hogbom niter off-by-one bug¶

    • Date noted: 2026-04-05
    • Status: likely CASA bug / legacy interface mismatch
    • Affected code:
    • casatools/src/code/synthesis/ImagerObjects/SynthesisDeconvolver.cc
    • casatools/src/code/synthesis/ImagerObjects/SDAlgorithmHogbomClean.cc
    • casatools/casacore/scimath_f/hclean.f
    • Source note: /Users/brianglendenning/Downloads/casa-hogbom-niter-findings (2).pdf

    Summary¶

    In the current CASA tclean(..., deconvolver='hogbom') path, niter=1 appears able to commit two clean components inside a single minor cycle while still reporting iterdone = 1.

    The effect is not limited to the top-level niter=1 case. Any CASA Hogbom minor-cycle call that enters hclean with a positive cycleNiter may commit one more component than the reported minor-cycle count. In a Cotton-Schwab run, that means the model, residual, restored image, and controller stop/refresh decisions can shift by up to one extra component per Hogbom minor-cycle block.

    The concrete repro described in the attached note used:

    • dataset: .../casatestdata/measurementset/vla/sim_data_VLA_jet.ms
    • setup: imsize=512, cell='12arcsec', specmode='mfs', weighting='natural', gain=0.1, threshold='0Jy', niter=1
    • observed result: CASA reported iterdone = 1, but the output .model image contained two nonzero clean components

    Likely mechanism¶

    The note points to an off-by-one style caller/kernel mismatch:

    1. SDAlgorithmHogbomClean::takeOneStep seeds starting_iteration = 0
    2. the Fortran hclean kernel iterates over an inclusive do iter = siter, niter
    3. the returned count is then clamped back down to niter

    With siter = 0 and niter = 1, that inclusive loop permits two update opportunities, which matches the observed behavior.

    Repro detail from the attached note¶

    The output .model image contained two nonzero pixels:

    1. (264, 331) = 0.6685306429862976
    2. (265, 331) = 0.6019284129142761

    Their sum matched the reported modelFlux, which makes this look like an actual extra component update rather than a display or reporting artifact.

    A second trace on the ALMA TW Hydra tutorial data used tclean(..., deconvolver='hogbom', niter=1, cycleniter=1, weighting='briggs', robust=0.5, imsize=250, cell='0.1arcsec'). CASA reported one minor iteration, but the model flux was 0.0569704 Jy; the dirty-image peak was 0.299844 Jy/beam, so one strict-gain component at gain=0.1 would account for only about 0.0299844 Jy. The reported model flux is therefore consistent with two committed Hogbom components in that minor-cycle call.

    Wave 3 heavy benchmark repro¶

    The same behavior appeared again during the ImPerformance Wave 3 standard-MFS heavy review on the retained Wave 2 medium VLA dataset:

    • dataset: /Volumes/GLENDENNING/casa-rs-imperformance/wave1/vla/single/medium/ms/wave1-vla-single-medium.ms
    • setup: specmode='mfs', gridder='standard', deconvolver='hogbom', imsize=1024, cell='0.25arcsec', spw='0:0~63', Briggs robust=0.5, gain=0.1, threshold='0Jy', niter=1, cycleniter=1
    • observed result: CASA reported iterdone = 1, but the output .model image contained two nonzero clean components:
    • (510, 510) = 9.177456855773926
    • (508, 507) = 8.556220054626465

    In a strict one-component casa-rs comparison this made the one-cycle residual RMS difference jump to 3.65e-2. Running casa-rs with its explicit CASA-compatible Hogbom accounting mode reproduced both components and reduced the residual RMS difference to 7.64e-5, matching the dirty gridding numerical floor. On the full niter=500, cycleniter=50 heavy row, the same CASA-compatible mode reduced the CASA/casa-rs product differences to .model RMS 1.71e-7, .residual RMS 5.68e-5, and .image RMS 5.87e-5.

    MatrixCleaner counts the iteration that stops it¶

    • Date noted: 2026-10-09
    • Status: CASA accounting quirk; casa-rs follows it for parity (IF-5, #654)
    • Affected code: synthesis/MeasurementEquations/MatrixCleaner.cc (MatrixCleaner::clean), read by SDAlgorithmMSClean::takeOneStep

    clean increments itsIteration at the top of each pass and only then tests the threshold (abs(strength) < threshold()) and the 50% divergence rule, so a step that stops on either reports one more iteration (numberIterations()) than it cleaned components. Multiscale iterdone, the niter budget and the per-cycle summaryminor counts include it; on refim_point with scales [0, 6, 10] CASA reports [22, 3, 25, 3, 47] for [21, 2, 24, 2, 51] components when the extra iteration is not charged. casa-rs charges it (Solver::charges_stop).

    Multiscale and multi-term scale convolutions shift by a pixel on odd image sizes¶

    • Date noted: 2026-10-09
    • Status: likely CASA bug; casa-rs does not follow it (IF-5, #654)
    • Affected code: synthesis/MeasurementEquations/MatrixCleaner.cc (makeScale, makePsfScales, makeDirtyScales), MultiTermMatrixCleaner.cc (computeRHS, computeHessianPeak)

    Scale functions are centred at (nx/2, ny/2) and convolved by FFT without moving that centre to the origin. Single convolutions are re-centred with FFTServer::flip, which rotates by ceil(n/2); double convolutions (PSF ⊛ scale ⊛ scale) are not flipped, relying on the two n/2 shifts cancelling. Both are exact only for even n: on an odd axis the scale- convolved residual is one pixel off its residual and the PSF cross terms one pixel off the PSF peak. casa-rs convolves with the scale centred at the origin, which agrees with CASA on every even axis.

    MatrixCleaner's step residual forgets earlier steps¶

    • Date noted: 2026-10-09
    • Status: likely CASA bug; casa-rs does not follow it (IF-5, #654)
    • Affected code: synthesis/ImagerObjects/SDAlgorithmMSClean.cc (takeOneStep), SDAlgorithmBase.cc (deconvolve)

    With cycleniter ≥ 5000 a plane's minor cycle runs in 2000-iteration takeOneStep calls. Each call sets the residual to itsDirty − PSF ⊛ (model − prevModel), where itsDirty is the residual at the plane's first step and model − prevModel only this step's components, so from the second step on the reported peak residual omits the earlier steps' subtraction. That peak drives the minor-cycle stop codes 2 and 4. casa-rs carries each step's residual into the next.

    Peak searches let rounding choose between equal pixels¶

    • Date noted: 2026-10-09
    • Status: CASA behaviour casa-rs follows (exact comparisons); it makes parity rows on exactly symmetric skies rounding-dependent (IF-5, #654)
    • Affected code: casacore/scimath_f/hclean.f, casacore minMax as read by MatrixCleaner::findMaxAbsMask and MultiTermMatrixCleaner (chooseComponent), Clark's ABSMAXF

    Every CASA peak search compares exactly and keeps the first extreme in its scan order; casa-rs does the same. On a point-symmetric sky such as refim_point, mirror pixels are equal in exact arithmetic (CASA's dirty and PSF images are exactly point-symmetric even in float32), and the scale convolutions and subtractions of the minor cycle break the tie by an ulp or two, so rounding, not the data, picks the component. On refim_point CASA's rounding went both ways: MatrixCleaner took the first mirror in scan order, and the multi-term cleaner the later one (one tie, at [50,47] / [50,53], value 4.9e-5, in the last cycle). casa-rs's FFTW plans are chosen by timing, so its refim_point multiscale row comes out at 5.4e-6 or 4.5e-2 NRMS from run to run; its MT-MFS row is 3.4e-4 when the tie goes CASA's way and 3.1e-2 when it does not (as on main). Both outcomes are equally valid cleans; such rows cannot measure parity, so IF-5's multiscale and MT-MFS acceptance uses skies without the symmetry (refim_twopoints_twochan, refim_eptwochan).

    The multi-term weight normalization override is never called¶

    • Date noted: 2026-10-11
    • Status: likely CASA bug; casa-rs follows it for parity (#704, PR #707)
    • Affected code: synthesis/ImagerObjects/SIImageStore.h, SIImageStoreMultiTerm.h, SynthesisNormalizer.cc (divideWeightBySumWt)

    SIImageStore declares virtual void divideWeightBySumwt() (lower-case wt). SIImageStoreMultiTerm declares void divideWeightBySumWt() (upper case W), a different name, so it overrides nothing; its loop that divides every Taylor weight image by the principal sum of weights is never called. SynthesisNormalizer::divideWeightBySumWt calls itsImages->divideWeightBySumwt(), which reaches the base body and divides weight(), term 0, alone. MultiTermFTNew::finalizeToSkyNew writes each term's raw getWeightImage moment, so .weight.tt1 and .weight.tt2 stay the raw Σ W·s^N while .weight.tt0 is normalized. CASA 6.7.6.14 on refim_alma_mosaic (mosaic, nterms=2) agrees: weight.ttN / sumwt.ttN is 0.6913 for N = 0, 1 and 2. casa-rs publishes the same.

    The analytic PB ignores a failed toPixel¶

    • Date noted: 2026-10-11
    • Status: likely CASA bug; casa-rs does not follow it (#702, PR #707)
    • Affected code: synthesis/TransformMachines/PBMath1D.cc (apply)

    PBMath1D::apply converts the pointing to a pixel with the image's direction coordinate (toPixel) and ignores the call's result, so a pointing the projection cannot place, such as one 90° or more from the image centre under SIN, is centred on whatever pixel the failed call left. casa-rs adds no beam for a pointing 90° or more from an image domain's centre and refuses any other projection failure.

    The cube Briggs weightor grids and looks up its density in different uvw frames¶

    • Date noted: 2026-10-15
    • Status: likely CASA bug; casa-rs does not follow it (#712 review by Fable and Astra)
    • Affected code (CASA 6.7.5.18 and 6.7.6.14):
    • casatools/src/code/synthesis/TransformMachines2/BriggsCubeWeightor.cc (weightUniform, getWeightUniform)
    • casatools/src/code/synthesis/TransformMachines2/GridFT.cc (put)

    BriggsCubeWeightor, which weighs cubes under uniform and Briggs weighting (perchanweightdensity), fills its density grid through GridFT::put, which rotates each row's uvw to the image phase centre (rotateUVW, GridFT.cc:778). It then looks each row up, and tapers it, at vb.uvw(), the unrotated MeasurementSet uvw (BriggsCubeWeightor.cc:826, 860-861). The grid and the lookup use different frames. When the phase centre is the field centre the rotation is the identity and nothing changes; for a cube with a phase centre away from the field centre, or a multi-field cube, a row reads the density of a different cell from the one its own sample was counted in, so its weight no longer follows the local density. The MFS weightor (VisImagingWeight) accumulates and looks up in one frame, the MeasurementSet uvw.

    casa-rs bins and looks up the cube rule at the rotated uvw, one frame for both (the_cube_density_bins_and_looks_up_the_rotated_uvw), and the standard (MFS) rule at the MeasurementSet uvw, as VisImagingWeight does (the_standard_density_bins_the_measurement_set_uvw). Cubes imaged at their own field centre agree with CASA either way; off-centre and multi-field cubes under a density weighting differ from CASA's weights by this mechanism.

    The Airy beam's blockage term uses the inverse length ratio¶

    • Date noted: 2026-10-21
    • Status: likely CASA bug; casa-rs follows it (#841, PR #843)
    • Affected code: synthesis/TransformMachines/PBMath1DAiry.cc (fillPBArray)

    For a dish of diameter D with a central blockage of diameter b, the voltage pattern is proportional to D²·jinc(x) − b²·jinc(x·b/D), where jinc(x) = 2J₁(x)/x and x = πDθ/λ. fillPBArray tabulates (areaRatio·jinc(x) − jinc(x·lengthRatio)) / (areaRatio − 1) with lengthRatio = D/b, so it evaluates the blockage term at x·D/b instead of x·b/D.

    IAU 2000 JMEAN to J2000 applies bias and precession in the wrong order¶

    • Date noted: 2026-10-22
    • Status: casacore bug; casa-rs does not follow it (#850)
    • Affected code: measures/Measures/MeasMath.cc (deapplyPrecession)

    Under IAU 2000, applyPrecession takes J2000 to JMEAN as in *= B; in *= P, v′ = Pᵀ·Bᵀ·v, with B the frame bias and P the precession. The inverse, deapplyPrecession, applies in = B·in and then in = P·in, which is P·B·v′, not B·P·v′. The two do not commute, so casacore's JMEAN→J2000 is not the inverse of its J2000→JMEAN: MECLIPTIC→J2000 and TECLIPTIC→J2000 are 0.14 mas off in 2026, and the error grows with time from J2000. casa-rs inverts exactly; the frame law compares the IAU 2000 ecliptics from the equator of date.

    CASA's gain screens read past their transform¶

    • Date noted: 2026-10-24
    • Status: CASA bug; casa-rs does not follow it (#841 Phase 3)
    • Affected code: synthesis/MeasurementComponents/CalCorruptor.cc (fBM::initialize, GJonesCorruptor::initialize)

    sm.setgain(mode='fbm') draws each antenna's amplitude and phase screens with fBM::initialize on n even slots of 5 s. It fills a half spectrum F of n/2 values, all but the last, and transforms it with FFTServer::fft into a real G whose length the server chooses: the last value's imaginary part is zero and the server was sized n, which is neither 2·(n/2) − 2 nor 2·(n/2) − 1, so G has n − 2 values for an even n and n − 3 for an odd one. It then copies n values out of G, the last two or three from past its end, and GJonesCorruptor::initialize scales each screen by its root-mean-square, those values included.

    What lies past the end changes from run to run. Measured with CASA 6.7.6: - three runs of corrupt-gain (tools/simulation/sm_corrupt_scenarios.json, the same seed) gave amplitude scales of 0.969, 0.966 and 1.005 of the documented one; - in a six-antenna probe with amplitude=[0.1], the phases' scale was 0.15 to 0.22 of it in one run and 1.0 in another; - with a table written, one run's last solution was unit gain, as zeros past the end would make it; - in one run of corrupt-gain-table, antennas 0–6 and 10 of 12 had unit gain throughout, their screens normalised by a value large enough to flatten them.

    casa-rs transforms every slot, so its screens have the documented scale. The CASA comparison holds CASA's gains to closure only, reports rather than checks CASA's unit-gain antennas, and compares the two implementations' screens by their autocorrelations, which a screen's scale does not change.

    settrop(mode='individual')'s water-vapour series come from the same fBM::initialize and normalise the same way (#841 Phase 4d): in one probe, antenna 0's phases were all below 5·10⁻¹⁰ rad. casa-rs transforms every slot there too. On fewer than six slots the spectrum's bins i < N/2 − 1 hold only the mean, so whatever varies in CASA's series is what it read past the transform; casa-rs refuses individual mode on so short a track rather than add no turbulence.

    tsys-manual noise takes stale or borrowed system temperatures¶

    • Date noted: 2026-10-24
    • Status: CASA bugs; casa-rs does not follow them (#841 Phase 3)
    • Affected code: synthesis/MeasurementComponents/CalCorruptor.cc (AtmosCorruptor::setCurrTime and simPar), synthesis/MeasurementComponents/SolvableVisCal.cc (setSimulate) and synthesis/MeasurementComponents/Jones.cc (JonesScal::invert, setMatByOk)

    setnoise(mode='tsys-manual') adds a unit-amplitude ANoise term and a T term flagged NoiseScale, whose inverse scales the noise: σ_ij = c a / sqrt(Δν t) · sqrt(Tsys(A_i) Tsys(A_j)) / (D_i D_j) (casa_simulation's corrupt::tsys has the whole formula). CASA computes the T table when setnoise is called, one solution per integration and spectral window, and applies it at corrupt by the nearest time. Measured on CASA 6.7.6 (the probe scripts and their results are on the NAS under casa-rs/issue-841-tsys-3a/probes; seven antennas of 12 m and 7 m, per-row variances over 32 to 128 channels): the formula holds to 4·10⁻⁴ (cross 0.99999 ± 0.00036, autocorrelations 1.0003 ± 0.0009, 12+12, 12+7 and 7+7 m pairs alike, and to 6·10⁻⁴ with every parameter away from its default), and CASA's T table, written with integrations of 120 s so that the cache below refreshes at each, gives every row's σ within 1.9·10⁻⁶ of casa-rs's (5,040 rows, two windows). But four inputs are not the row's own:

    • The airmass is up to 100 s stale. simPar caches each antenna's airmass and setCurrTime recomputes it only when the solution time has moved more than 100 s since (the comment's intent is a 1 % tolerance at elevations above 5°). At 10 to 14° elevation with τ₀ = 1 and 2 s integrations, CASA's per-integration variance against the formula at the integration's own time rises in a sawtooth with a 102 s period from 1.01 to 1.56, 1.176 ± 0.0014 on average. The cache is not reset at a field change either.
    • Rows observed after setnoise take another integration's solution. The table holds only the integrations observed by then; a scan observed later is scaled by the nearest one. A scan at 51.6° elevation observed after setnoise got the noise of the earlier scan's last integration at 72.7°: 0.666 ± 0.002 of its own variance (τ₀ = 0.5).
    • Every row takes the first row's EXPOSURE (exposure()(0)): after settimes changed the integration time from 10 s to 2 s, the 2 s scan's variance was 0.1999 of its own, 0.9994 of the first row's.
    • An antenna without an unflagged row applies as 1. setSimulate skips fully flagged rows, so a shadowed or low antenna gets no solution; JonesScal::invert marks it bad and setMatByOk applies it as 1. Its rows get the unit noise times the other antenna's scale (variance 1.0006 of 1 Jy² when both are bad, 1.009 of s_j² when one is).

    casa-rs computes each row's σ from its own integration: each antenna's airmass at the phase centre at the row's TIME, the row's EXPOSURE, its window and dishes, whatever the flags and whenever the row was observed. The CASA comparison scenarios (tools/simulation/sm_noise_scenarios.json) observe above 40° elevation with one integration time and no flagged rows, where the stale airmass moves Tsys by under 0.1 %. casa-rs keeps CASA's rule for a T that is not finite and positive (Tsys overflowing single precision below the horizon, airmass 1000): that antenna scales by 1.

    A tsys-manual term scales every noise term¶

    • Date noted: 2026-10-24
    • Status: CASA bug; casa-rs does not follow it (owner, 2026-10-24: follow CASA only if its product is the better simulation, which it is not; #841 Phase 3)
    • Affected code: synthesis/MeasurementEquations/VisEquation.cc (collapseForSim)

    collapseForSim first adds every ANoise term's noise to DATA, then applies every NoiseScale T term to DATA, in correct mode. So each tsys-manual term's scale multiplies the noise of every term, its own and the others'. Measured on CASA 6.7.6: two tsys-manual terms of one seed gave variance 4 σ⁴ (1.004 of it) rather than 4 σ², in Jy⁴, and a 0.5 Jy simplenoise term with a tsys-manual term gave (0.25 + 1) σ² (0.998 of it) rather than 0.25 + σ²: the 0.5 Jy noise came out scaled by the system temperature. casa-rs adds each term's noise with its own σ, as simplenoise terms add, so simplenoise's σ stays in Jy whatever else is set; terms of one seed still add coherently. simobserve sets one noise term and never reaches this.

    CASA's product has no physical counterpart. A system temperature is the sum of its contributions (receiver, atmosphere, spillover, CMB), which a single tsys-manual term already models; a baseline's noise variance scales as the product of its two antennas' system temperatures; and the powers of uncorrelated noise add (Thompson, Moran & Swenson, Interferometry and Synthesis in Radio Astronomy, 3rd ed., pp. 55, 266, 386 and 733). Multiplying one term's σ by another's gives Jy², not a noise in Jy.

    tsys-atm noise takes its atmosphere half a band below each channel¶

    • Date noted: 2026-10-24
    • Status: CASA bugs; casa-rs does not follow them (#841 Phase 4c)
    • Affected code: synthesis/MeasurementComponents/CalCorruptor.cc (AtmosCorruptor::initAtm, tsys, opac) and synthesis/MeasurementComponents/SolvableVisCal.cc (setSimulate)

    setnoise(mode='tsys-atm') scales a unit ANoise by a Tf term ("TF NOISE") whose Tsys comes from ATM for each channel: Tsys(A, c) = (hν/k) e^(τA) (1/(e^(hν/k/T_ebb(A)) − 1) + T_rx/(hν/k)) (1 + g), τ the zenith opacity and T_ebb the sky's equivalent blackbody temperature at airmass A, with hν/k from the channel's frequency (casa_simulation's corrupt::tsys_atm has the whole model). Measured on CASA 6.7.6 (ALMA's site defaults, 1 mm of water, 64-channel windows of 100 MHz from 180 GHz, across the 183 GHz line, and from 321 GHz, 2 s integrations; the probe scripts and results are on the NAS under casa-rs/issue-841-tsys-4c), every channel's noise variance agrees with that formula, through casa-atmosphere, with no free parameter (ratio 1.0000 and 1.0027, rms 0.0106 and 0.0100 per channel, against a statistical 1σ of 0.0149) once the atmosphere is taken at the frequencies CASA gives ATM, which are not the channels':

    • The atmosphere is half a band below the channel. initAtm builds each window's ATM grid from REF_FREQUENCY, which the simulator sets to the first channel's frequency, with the reference at the middle channel: ATM's channel i is at REF + (i − n/2)·Δν for the first window and REF + (i − n/2 − 1)·Δν for the others, and opac and tsys read channel c of that grid. So channel c's τ and T_ebb are those of a frequency half the band below it (3.2 GHz for the probe's windows), while hν/k is the channel's own. Against the atmosphere at each channel's own frequency, CASA's variance across the 183 GHz line is off by a mean factor of 6.1 and up to 103; at 321 GHz by 0.39 on average and up to 5.5. The shift grows with the window's width and matters wherever the atmosphere changes across it: the 183 GHz line's brightness changes by tens of kelvin over a few GHz at a 5,000 m site (Thompson, Moran & Swenson, Interferometry and Synthesis in Radio Astronomy, 3rd ed., p. 746, Fig. 13.21), and an ozone line at 231.7 GHz nearly doubles ALMA's system temperature within a band (B. Svoboda, Special Topics: Spectral Lines, NRAO Synthesis Imaging Workshop 2026, slide 18).
    • A one-channel window after the first gets no Tsys. For n = 1 the later windows' channel map is read past its end, which is undefined behaviour. In CASA 6.7.6 on macOS the index it read pointed past the grid (the log reads "ch 972849296/20"); the term's T came out bad, setMatByOk applied it as 1, and the probe's 2 GHz continuum window at 230 GHz got unscaled 1 Jy noise (variance 0.996 Jy²). Another build may read something else.

    casa-rs evaluates ATM at each channel's CHAN_FREQ, for every window and a one-channel window alike, so a channel's σ follows the sky it observes. As for tsys-manual, each row takes its own integration's airmasses and EXPOSURE (stale and borrowed system temperatures); the term is also refused when its zenith Tsys at the first window's centre is not a number, which CASA's check (> 10⁶ K or ≤ 0) lets through.

    settrop's screen has an anisotropic spectrum¶

    • Date noted: 2026-10-24
    • Status: CASA bugs; casa-rs does not follow them (#841 Phase 4d)
    • Affected code: synthesis/MeasurementComponents/CalCorruptor.cc (fBM::initialize, two dimensions)

    settrop(mode='screen') blows one two-dimensional screen of fractional Brownian motion across the array. fBM::initialize fills a half spectrum F2(i, j), i along the wind (the half axis) and j across it, with amplitudes |(i, j)|^−(β+½)/2 times a normal draw (its comment: "still something not quite right with exponent"; an earlier line, left commented out, had −(β+1)/2):

    • The wavenumbers are indices. The screen is long along the wind (CASA's probe screen was 1,359 by 271 pixels), so an index along it is a fifth of the wavenumber of an index across it: the spectrum is stretched along the wind, and the screen is not isotropic.
    • The full axis is not wrapped. j runs to the screen's width, where the indices past half of it are negative wavenumbers; taking them as large ones gives the negative wavenumbers the smallest amplitudes.
    • The exponent. A two-dimensional fractional Brownian motion whose cuts have the spectral exponent β (as individual mode's series, and beta's documentation, have it) has amplitudes |k|^−(β+1)/2.
    • Out of bounds. It sets the imaginary parts of F2(s0/2, 0) and F2(s0/2, s1/2), one past the end of the half axis's s0/2 entries, and a half axis of s0/2 entries transforms to s0 − 2 real pixels along the wind, of which it copies s0: the last two from past the end of the output, as the one-dimensional series do (gain screens read past their transform). CASA's own settrop test is skipped for "intermittent failures".

    Isotropic turbulence's phase spectrum depends only on the spatial frequency's size, |q|^−11/3 in two dimensions (Thompson, Moran & Swenson, 3rd ed., sec. 13.1.7, p. 725). casa-rs draws |k|^−(β+1)/2 on the wavenumbers in cycles per pixel, the full axis wrapped, with the conjugate pairs and real bins the real transform needs on the half axis's first and Nyquist columns (drawn apart, those modes come out at half the power), and transforms every pixel: on a screen five times as long as wide its structure function is the same along the wind and across it, where CASA's differ by five, and its boundary modes have their interior neighbours' power (corrupt::troposphere's unit tests).

    • Affected code: synthesis/MeasurementComponents/VisCalSolver2.cc:180–185 (and :353–358, the other solve overload), CASA 6.7.5.18

    tsdimaging's theoretical beam models the kernels, not the gridder's¶

    • Date noted: 2026-10-28
    • Status: CASA behaviour casa-rs does not follow (#938 part 1, #841 Phase 6c)
    • Affected code: casatasks/src/private/sdbeamutil.py (TheoreticalBeam.get_kernel and the kernel functions it calls)

    tsdimaging gives its image the beam sdbeamutil.TheoreticalBeam computes: the antenna's Gaussian beam convolved with a cut through the gridding kernel and with a box as wide as the sampling, then fitted with a Gaussian. The kernel it convolves with is not the gridder's (SDGrid::init) but a model of it, and the models disagree with the gridder: - GAUSS. The gridder takes gwidth as a half width at half maximum; sdbeamutil passes it to a Gaussian that takes a full width. It also cuts the kernel at 1.5 gwidth where the gridder cuts at truncate (default 3 gwidth). - GJINC. sdbeamutil ignores truncate ("NOT SUPPORTED YET") and always cuts at the jinc's first null. - SF. The gridder's kernel is (1 − ν²) grdsf(ν); sdbeamutil uses SciPy's prolate spheroid pro_ang1(0, 0, c) with c = 5.356π/2, chosen to resemble it. - PB. The gridder takes the telescope's power pattern (for ALMA, the 10.7 m Airy pattern of VPSkyJones); sdbeamutil takes an Airy disk scaled to the Gaussian beam's width, for the antenna's own diameter. - BOX. sdbeamutil makes the box one pixel wide whatever convsupport is; the gridder's box reaches 2s + 1 pixels.

    The reported beam is then not the image's. Against CASA 6.7.6 on the oracle's setups (tools/singledish/tsdimaging_oracle.py), the gridder's own kernels give beams wider by 0.60% to 3.3% for GAUSS, and 0.31% narrower for GJINC with a truncate. They differ by at most 6.0e-4 for SF, PB and GJINC at its defaults. The gridder reads its table at the radius truncated to a hundredth of a pixel, which widens the kernel slightly. That accounts for all of GJINC's difference at its defaults (read at the rounded radius, it agrees with CASA to 1e-6) and for about 40% of SF's. The rest of SF's is SciPy's spheroid against grdsf.

    casa-rs cuts through the gridder's own table (casa_imaging_singledish:: theoretical_beam_arcsec), so the beam describes the image the gridder makes. BOX at its default support, which both describe alike, agrees with CASA to 2e-8.

    The cost falls downstream. simanalyze and simalma grid total power with SF of support 6 and scale its flux by this beam's area. A beam 6e-4 wider is an area about 1.2e-3 larger, so their scaled total-power and feathered products differ from CASA's by about that factor, at the edge of the 1e-3 acceptance. Phases 6g and 6h measure it.

The Python int is narrowed to casacore's 32-bit Int without a range check. casa-rs stores a new keyword whose value does not fit 32 bits as a 64-bit integer, and refuses such a value for an existing 32-bit keyword with RuntimeError: ... does not fit the integer keyword NAME, which holds fewer bits, rather than store a wrong number.

    tb slices with a wrong rank or a start outside the array abort the process¶

    • Date noted: 2026-10-30
    • Status: CASA bug; casa-rs does not follow it (#1025, the table tool)
    • Affected code: casatools table::getcellslice, getcolslice, putcellslice and putcolslice, over casacore's Slicer

    In CASA 6.7.6.14 a slice whose blc, trc or incr has the wrong number of elements for the array, or whose blc lies outside the array, throws an ArraySlicerError that nothing catches, and the Python process ends (libc++abi: terminating due to uncaught exception of type casacore::ArraySlicerError, exit status 134). The default incr=[1] is such a slice for an array of more than one axis, so tb.getcellslice('DATA', 0, [0, 0], [1, 3]) aborts. casa-rs raises a RuntimeError for each of them and takes a one-element incr as the step of every axis. The recording (crates/casars-python/python/tests/data/casa_table_tool.json, slices and ms_slices) holds only the cases CASA survives. CASA is also inconsistent about trc=-1: getcellslice refuses it ("All elements of trc must be greater than or equal to 0"), getcolslice takes it as the last element; casa-rs follows both.

    tb.putcell and putcol wrap an int beyond 32 bits in an int cell¶

    • Date noted: 2026-10-30
    • Status: CASA bug; casa-rs does not follow it (#1025, the table tool)
    • Affected code: casatools ValueHolder conversion to a column's type

    tb.putcell('ANTENNA1', 0, 2147483648) returns True and the cell then holds -2147483648; -2147483649 becomes 2147483647 and 4294967297 becomes 1 (CASA 6.7.6.14; the int_overflow scenario of crates/casars-python/python/tests/data/casa_table_tool.json, which the replay leaves out). putcol wraps the same way. A Python int is narrowed to the 32-bit column type without a range check, as for putkeyword above. casa-rs raises RuntimeError: a value is out of range for a column of Int and leaves the cell, rather than store a wrong number. Astra's review of #1034 noted the departure.

    tb.putcell with several rows writes those before a missing one¶

    • Date noted: 2026-10-30
    • Status: CASA behaviour that casa-rs does not follow (#1025, the table tool)
    • Affected code: casacore TableProxy::putCell

    tb.putcell('id', [0, 3], 22) on a table of three rows writes row 0, then fails on row 3 with no such row: TableProxy::putCell checks and writes one row at a time, so a call that raises has still changed the table (rows_vector scenario). casa-rs checks every row first and raises with the table as it was. The recording follows the failed call with a write that puts row 0 back, so that its later reads agree.

    tb.addrows with a negative count removes rows¶

    • Date noted: 2026-10-31
    • Status: CASA bug; casa-rs does not follow it (#1025, the table tool)
    • Affected code: casacore TableProxy::addRow (the count is an Int handed to Table::addRow(rownr_t))

    tb.addrows(-1) on a table of three rows returns True and leaves two; addrows(-2) leaves none, and the table reopens with no rows (addrows_negative scenario).     tb.removerows and tb.addcols do part of a call that fails¶

    • Date noted: 2026-10-31
    • Status: CASA behaviour that casa-rs does not follow (#1025, the table tool; Astra's review of #1036)
    • Affected code: casacore BaseTable::removeRow(Vector) and TableProxy::addColumns

    tb.removerows([2, 2]) on a table of three rows removes the first row 2, then raises "rownr 2 too high ... (#rows=2)", leaving two rows: the row numbers are taken from the highest down and each is checked against the table as it then is. (A number beyond the table, even among valid ones, fails before any row goes: it is the highest.) tb.addcols of aaa and id on a table that has id adds aaa and then raises "column already exists": addColumns builds the whole description first (a malformed field fails the call with nothing added) and then adds the columns one by one, in the record's sorted order (structure_partial scenario). casa-rs checks the whole call before it changes anything: both raise CASA's message and leave the table as it was. The successful calls, repeats included (removerows([0, 0]) removes two rows), are CASA's.

    importfits reads every FITS date as UTC¶

    • Date noted: 2026-10-30
    • Status: CASA bug; casa-rs does not follow it (#1017)
    • Affected code: casacore coordinates/Coordinates/FITSCoordinateUtil.cc (getObsInfo, which reads TIMESYS from the header record, and the WCS date wcslib holds)

    exportfits writes an image's observation date in the epoch's own time scale, DATE-OBS with TIMESYS naming the scale (ObsInfo::toFITS). importfits gives the date back with the same calendar value but labelled UTC, whatever TIMESYS says. An image observed at 2020-05-31 12:00 TAI exported by CASA 6.7.6 with TIMESYS = 'TAI' imports at 2020-05-31 12:00 UTC, 37 seconds later. Where the scale is lost was not pinned down: getObsInfo reads TIMESYS from the header record and the date from wcslib's mjdobs, so the scale is gone by then. casa-rs reads MJD-OBS or DATE-OBS in the scale TIMESYS names, UTC when it names none (casa_coordinates::fits::from_fits_header), so the round trip keeps the date.

    feather fails on an image whose direction is not on its first two axes¶

    • Date noted: 2026-10-30
    • Status: CASA limitation; casa-rs does not follow it (#1002, PR #1022 review)
    • Affected code: casatools synthesis/MeasurementEquations/Feather.cc (its FFT, cursor and weight-image paths)

    feather finds an image's direction axes for part of its setup, but its lattice cursors and FFTs assume the direction plane is the first two axes. CASA 6.7.6.14's feather of a pair of 16 by 16 pixel images, one Stokes and two channels, with 2″ and 6″ beams, succeeds over [RA, Dec, Stokes, Freq]. The same pair over [Stokes, RA, Dec, Freq] or [Freq, RA, Dec, Stokes], as imtrans makes it, fails with LatticeStepper::setCursorShape: cursorShape <=0 or > latticeShape. casa-rs feathers each direction plane wherever its axes are. The transposed pair's result is the transpose of the direction-first pair's (casa-images casa_axis_maps test feather_takes_the_direction_wherever_its_axes_are), and the direction-first result is checked against CASA's in image_analysis_casa.

    tb.copyrows adds the rows before it finds a cell it cannot convert, and wraps integers¶

    • Date noted: 2026-10-31
    • Status: CASA behaviour that casa-rs does not follow (#1025, the table tool; Astra's review of #1039)
    • Affected code: casacore TableCopy::copyRows and ROTableRow/TableRow::put (RecordInterface::as...)

    copyRows adds an output row and then puts its cells one by one. When a shared column has a type the input's cell cannot be converted to (a double output column for a dcomplex input, RecordInterface::asDouble - invalid data type; an int output column for a float array input, TableRecordRep::get_pointer - incorrect data type used for field ...), the call raises with the rows already added and their cells never set: reading them gives whatever the heap held (copyrows_types scenario of crates/casars-python/python/tests/data/casa_table_tool.json, which does not compare the table after a refusal). casa-rs checks the types before it changes anything and raises with the output table as it was.

    Which conversions CASA accepts was probed pair by pair and is what casa-rs accepts (tools/table/cell_convert.rs), with one exception: an integer that does not fit the output column's type is wrapped as a C cast does (a Short -5 becomes the uChar 251, a uInt 4294967291), the same narrowing as putcell above. casa-rs raises RuntimeError: a value is out of range for a column of ..., before the output is touched, rather than store a wrong number.
